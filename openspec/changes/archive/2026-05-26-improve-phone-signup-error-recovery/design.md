## Context

当前手机号注册链路已经区分出几类密码页硬失败：

- `Incorrect phone number or password`
- “该手机号已存在”
- 认证重试页中的 `fraud_guard`

这些分支都会终止当前轮，清空注册手机号运行态，并回到步骤 1 重新获取号码。相对地，密码页内联提示“创建帐户失败，请重试”目前没有被识别成硬失败，因此共享恢复逻辑只会看到“仍停留在密码页，且继续按钮还可点击”，于是继续重复点击“继续”。

另外，当前手机号来源既可能来自接码平台，也可能来自手动输入。部分 provider 返回的值不带 `+`，而“登录或注册”页手机号输入逻辑没有统一补齐前缀，导致号码格式依赖上游返回值。

这次变更只修复这两个共享行为，不扩展新的 provider 能力，也不重构手机号架构。

## Goals / Non-Goals

**Goals:**

- 把密码页“创建帐户失败，请重试”识别为手机号注册链路中的不可恢复错误。
- 命中该错误时，停止当前页重复点击，改为释放当前 activation（如存在）并回到步骤 1 重开当前轮。
- 在手机号填入“登录或注册”页前，统一补齐缺失的 `+` 前缀。
- 保持修复范围局限在手机号注册共享链路，不影响邮箱注册路径。

**Non-Goals:**

- 不把所有 `something went wrong` 文案都升级为硬失败。
- 不新增接码 provider 或修改 provider 优先级逻辑。
- 不改动手机号国家选择、价格策略或验证码轮询策略。
- 不引入新的侧边栏配置项。

## Decisions

### 1. 仅将密码页内联“创建帐户失败，请重试”识别为手机号注册硬失败

在密码页状态快照中新增一类明确匹配：

- 中文：`创建帐户失败，请重试`
- 英文等价：`unable to create your account` / `couldn't create your account`

但只在“当前链路是手机号注册，且页面仍是密码页”时生效。

原因：

- 该文案与截图中的实际问题一一对应，误判面最小。
- 当前系统已经对手机号/密码不匹配类错误有“重开当前轮”的成熟处理方式，可以复用同类收口。

备选方案：

- 把所有 `something went wrong` 一并视为废号。拒绝，因为认证页、网络超时页和密码页内联错误都可能复用该文案，误判面太大。

### 2. 复用现有“丢弃注册手机号并回到步骤 1”机制，而不是新建一条平行重开链路

命中这类错误后，沿用现有的“清空 `signupPhoneNumber / signupPhoneActivation / signupPhoneCompletedActivation` 并重开当前轮”的框架，只增加一个新的错误前缀或错误分类。

原因：

- 现有自动重开、日志和状态清理已经覆盖手机号注册硬失败。
- 这样可以保持 auto-run、手动单步执行和运行态持久化的行为一致。

备选方案：

- 在内容脚本里直接刷新或返回上一步。拒绝，因为它绕开了后台现有的轮次状态机和 activation 清理逻辑。

### 3. 在重开前 best-effort 取消当前 activation

如果当前运行态存在 `signupPhoneActivation`，后台在清空状态前先调用既有 provider 取消接口：

- HeroSMS / SMSBower：`setStatus(8)`
- 5sim：`/user/cancel/<id>`
- NexSMS：关闭 activation

失败仅记日志，不阻止当前轮重开。

原因：

- 释放号码能减少占单时间和不必要的成本。
- 当前各 provider 已有统一取消入口，可直接复用。

备选方案：

- 只清本地状态，不释放远端 activation。拒绝，因为这会保留无效占单，收益太低。

### 4. 在提交到“登录或注册”页之前统一规范化手机号

新增共享的号码归一化规则：

- 去掉首尾空白。
- 如果号码为空，不做改写。
- 如果号码第一个字符不是 `+`，则在前面补一个 `+`。

该规则只用于页面填写值，不改变 provider 原始返回记录之外的其他业务语义。

原因：

- 目标页面对国际号码格式更敏感，统一补齐后更稳定。
- 规则简单，且与用户给出的示例完全一致。

备选方案：

- 在 provider 层强制所有返回值都带 `+`。拒绝，因为号码也可能来自手填或其它运行态来源，页面提交前统一规范化更稳妥。

## Risks / Trade-offs

- `[文案匹配过宽导致误判]` → 仅匹配密码页内联文案，并限制在手机号注册场景触发。
- `[释放 activation 失败]` → 采用 best-effort；失败只记日志，不阻塞当前轮重开。
- `[补 `+` 与极少数本地格式输入冲突]` → 仅在提交到手机号登录/注册页前使用，且只对缺失前缀的号码补齐，不改动已有 `+` 号码。
- `[新增一类硬失败后改变重试节奏]` → 这是有意调整，目的是用“快速重开”替换“无效重复点击”。

## Migration Plan

1. 在内容脚本密码页状态识别里加入“创建帐户失败，请重试”的专用检测。
2. 在后台错误分类中把该检测接到现有“清空注册手机号并重开当前轮”逻辑上。
3. 在触发重开前调用现有 signup activation 取消能力，并以 best-effort 方式记录结果。
4. 在手机号填写“登录或注册”页之前增加号码规范化。
5. 补回归测试，验证：
   - 密码页内联错误会停止重复点击并触发重开
   - activation 会尝试取消
   - 不带 `+` 的号码会被补成带 `+` 的值

回滚策略：

- 本次改动局限在错误识别和输入归一化层。
- 如需回滚，移除新增错误匹配和补 `+` 归一化逻辑即可，不涉及状态迁移。

## Open Questions

- 英文错误文案是否需要在首次实现时一并覆盖，还是先只覆盖中文文案；实现时可按现有页面快照决定。
- “补 `+`” 的归一化是否应同时用于后续 add-phone 等其它手机号输入页；本次 change 默认只要求覆盖“登录或注册”页。
